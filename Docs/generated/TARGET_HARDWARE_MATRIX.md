## 2. STEAM DECK (Proton/Linux) PATH

### 2.1 Is FSR 4.x usable on the Deck today? **No.**

Three independent gates each close, and all three must open:

1. **Hardware gate — closed, and it will not open via the 26.10.1 driver.**
   AMD's FSR Upscaling requirements state: *"AMD FSR™ Upscaling 4.1.1: AMD Radeon™ RX 9000 and 7000 Series discrete GPUs. Requires Shader Model 6.6 support"* and *"AMD FSR Upscaling 4 requires an AMD Radeon RX 9000 or RX 7000 Series discrete GPU or better. When running on other hardware the API will automatically select AMD FSR 3.1.5."*
   GPUOpen further states backward compatibility runs *"through analytical upscaling paths with AMD FSR 3 for RDNA 3.5 and RDNA 2 architecture and older GPUs."*
   The Deck's APU is **RDNA 2 (VanGogh, SM 6.2)** — below the SM 6.6 floor and not a discrete RX 7000/9000 part. (Note the same AMD table says FSR 3.1.5 and FG 3.1.6 need only **SM 6.2**, and FG 3.1.6 needs "RX 5000 Series Graphics and above (or equivalent from other GPU vendors)" — so the Deck *does* satisfy the fallback tier's requirements. It fails the 4.x tier, not the 3.x tier.)
   The 26.10.1 release **did** add FSR 4.1 to *RDNA 2* — but specifically to **RX 6000 Series discrete graphics products** ("AMD optimized the INT8 model originally created for FSR Upscaling 4.1 on RX 7000 Series GPUs, enabling support for RX 6000 Series GPUs first released in 2020"). A VanGogh APU is not an RX 6000-series card. AMD's 26.10.1 support list is explicit and closed: RX 6000 Series, Ryzen AI Max 300/400, Ryzen AI 9 300/400. **The Deck appears on none of them.** **Important precedent, so "RDNA 2 cannot do FSR 4.1" is not overstated:** AMD's own announcement says the handheld APUs get FSR 4.1 via *"a new, more efficient version of AMD FSR Upscaling 4.1 that is purpose-built for the class of hardware that includes AMD Ryzen AI 9 and AMD Ryzen AI Z2 Extreme/Ryzen Z2 Extreme/Ryzen Z2 A processors"* — and the **Z2 A is RDNA 2**. So RDNA 2 APU silicon is not inherently excluded from FSR 4.1. What excludes the Deck is that (a) the Deck is **not** an AMD-named FSR 4.1 part, (b) Adrenalin explicitly *"does not include support for handheld gaming devices. Users should check with the OEM for device specific drivers"*, and (c) the Deck has no OEM driver in the FSR 4.1 list. The Z2 A gets a bespoke small model; the Deck gets nothing. (AMD's own FSR technology page still carries the older line *"support for RX 6000 Series Graphics launching in 2027"* — that page is stale relative to the 2026-10-20 release notes, which shipped early; the release notes are the newer, authoritative document.)

2. **Delivery gate — closed on SteamOS.**
   AMD's mechanism is explicitly a **driver-side swap of the ML DLL**: "future AMD Software: Adrenalin Edition driver releases can update the version of ML-based technologies used in-game by default. This ensures players experience the latest available technology without requiring game updates for each title", and "Games which have previously integrated AMD FSR 3.1 and later are eligible for automatic version upgrades to ML-powered AMD FSR Upscaling 4.1.1 via future AMD Software: Adrenalin Edition releases on AMD Radeon RX 9000 and 7000 Series GPUs (**DX12 only**)". The 4.1.2 upscaler revision that ships in Adrenalin 26.10.1 is delivered to games by that same **Windows driver** ("AMD Software: Adrenalin Edition does not include support for handheld gaming devices. Users should check with the OEM for device specific drivers"). SteamOS has no Adrenalin. The vendor tree in this project is **FSR 4.1.1** (`Plugins/FSR/FSR.uplugin` → `VersionName: 4.1.1`, UE 5.8 tree `FSR-580`) — it does not contain 4.1.2, and 4.1.2 is not in any released SDK. **FSR 4.1.2 is not reachable by this project on any node, Windows or Linux.**

3. **API gate — closed.**
   FSR SDK 2.3 supports **DirectX 12 only** for upscaling ("AMD FSR SDK 2.3 … Supports: DirectX® 12"). AMD's own footnote also ties the SM 6.6 tier to the DX12 toolchain: "Shader Model 6.6 support requires DirectX 12 Agility SDK 1.4.9 or later" — a Windows-only dependency that does not exist on the Steam Deck's Linux/Proton stack. AMD announced at the 2026-10-20 newsroom event that FSR 4 is *"making its way to the Vulkan API"*, with the Linux community tracking it as landing in **FSR SDK 2.4** — which has not shipped. So the native Linux/Proton path has no FSR 4.x upscaler DLL to call.

**Conclusion (plain statement):** with SDK 2.3.0 being DX12-only and Vulkan FSR 4.1 unreleased (SDK 2.4 pending), **FSR 4.x is not usable on the Steam Deck today** — not on the native Linux path, and not on the DX12-in-Proton path either, because the *hardware* (RDNA 2, SM 6.2) fails AMD's own FSR 4.1 requirement before the API question is even reached. The Deck's only correct tier is **FSR 3.1.5**, which is what `CommanderDeckRDNA2` already forces.

### 2.2 What the FSR 3.1.5 fallback means for Deck resolution and perf targets

- **Resolution.** The Deck's native panel is 1280×800. `CommanderDeckRDNA2` sets `QualityMode=3` → Performance, a **2.0× upscale → 50% render scale**, i.e. an internal **640×400** buffer upscaled to 1280×800. That is a 4:3-ish internal resolution being stretched to 16:10, so expect softness that is *not* ML-reconstructed detail — FSR 3.1.5 is an analytical (Laplacian + temporal) upscaler, so fine detail is reconstructed from heuristics, not inferred by a neural model. The 4.x path exists precisely because 3.1.5 loses detail at these ratios.
- **Perf.** The 50% scale is a memory-bandwidth and shading decision made for the 8-CU RDNA 2 APU. It buys headroom, not image quality. Any 4.1-class gain is **not** available to this node, so the Deck's frame budget must be planned around FSR 3.1.5 + FSR 3.1 frame generation only.
- **Frame generation.** FSR 3.1 FG (optical flow) is the only FG tier the Deck can use. Whether the UE plugin's `FFXFrameInterpolationApi` path actually engages **under Proton/DXVK on Deck silicon is UNVERIFIED** — this project has never run a frame-gen session on the Deck, and DXVK-mediated optical flow is a known rough edge on SteamOS. Treat Deck FG as *plausible, unproven*.
- **Plugin reachability (structural, not a tuning issue).** `Plugins/FSR/FSR.uplugin` declares `SupportedTargetPlatforms: ["Win64"]`, and the FFXD3D12/FFXD3D12Backend modules carry `PlatformAllowList: ["Win64"]`. The same Win64-only scoping applies to the DLSS, StreamlineNGXCommon and XeSS plugins in `TheCommander.uproject`. So **a native Linux build of this project contains none of the three upscaler plugins** — the only way the Deck can reach FSR 3.1.5 at all is by running the **Win64 build under Proton (DXVK → Vulkan on RADV)**. The Deck does have Proton: GE-Proton7-28 plus Proton 7.0 / 8.0 / 11.0 / Hotfix / Experimental and SteamLinuxRuntime sniper & soldier (all OBSERVED).
- **Deck hardware facts to design against (OBSERVED):** SteamOS "holo", kernel `6.18.50-valve2-1-neptune-618-gc7289a96b14d`, Mesa **26.2.0-devel** with RADV driver 26.1.99, Vulkan **1.4.350**, DMI `product_name=Jupiter` / `product_version=1` / `vendor=Valve` → **original 2021 Steam Deck (LCD)**, APU 0405, CPU family 23 model 144 step 2 (Zen 3), 8 RDNA 2 CUs (Valve spec), 1 GB fixed VRAM aperture, 16 GB system RAM (14 GiB visible to the OS).

## 4. Corrections and open assumptions

1. **The "SM 6.7-class verification host" label in the existing profile doc is not reproducible.**
   `Docs/generated/PERFORMANCE_UPSCALER_PROFILE.md` §2.1 and `upscaler_proof_log.txt` header both describe the verification host as "shader model 6.7". The local machine's own adapter is **`0x1636` (Renoir-class, RDNA 2)**, and `dxdiag` reports **Feature Levels 12_1, 12_0, 11_1, 11_0, 10_1, 10_0, 9_3, 9_2, 9_1** — a *feature level*, not a shader model. RDNA 2 silicon is **SM 6.2**; SM 6.7 is RDNA 3 (gfx11). The "6.7" figure appears to be a feature-level/architecture mix-up. Every conclusion in the profile doc that depends on "SM 6.7-class" — in particular the framing of `CommanderRDNA3Desktop` as a tier-0-loader profile — is therefore **UNVERIFIED** as stated. Flagged, not fixed: `Docs/` and `Config/` are out of scope for this task.
2. **"RX 7600 XT" on HTPC.** Observed SKU strings read "RX 7600" (lspci Navi 33, `1002:7480`; vulkaninfo "AMD Radeon RX 7600 (RADV NAVI33)"). Same PCI ID covers 7600/7600 XT/7600S/7700S. VRAM 8 GB confirmed (`mem_info_vram_total` 8573157376). XT-vs-non-XT: **UNVERIFIED**.
3. **HTPC has no role in the Commander's declaration.** It is not a build node, test node, or ship node. Its RX 7600 is an RDNA 3 dGPU and would be FSR 4.1.1-eligible *if* a Windows/Proton path were stood up; as a native Linux box the Win64-only FSR plugin does not exist in the build. **UNVERIFIED** and out of scope until the Commander assigns a role.
4. **MAIN has no UE 5.8 engine installed.** `D:\` on MAIN has no `Unreal_Engine` directory, and `C:\Program Files\Epic Games` contains only `Launcher`, `DirectXRedist`, `GameInputRedist`. The engine lives on the **LAPTOP** (`D:\Unreal_Engine\UE_5.8`). All three proof-log runs therefore executed on the laptop's RDNA 2 iGPU — including the ones labelled `Deck` and `RDNA3`. MAIN is the declared primary build node but currently has no engine to build with. Whether MAIN is expected to receive an engine install is **UNVERIFIED**.
5. **MAIN's driver is current but its FSR tier is unproven.** MAIN runs Adrenalin **26.10.1** with driver `32.0.32015.7029` (2026-10-18) — the 26.10.1 release is what makes FSR 4.1.1 live on RX 7000-series, and the driver also auto-updates FSR version for games that integrate AMDFSR 3.1. Our vendor tree is 4.1.1, so 4.1.1 is the ceiling. Whether the FFX runtime's own device check accepts the 7900 XTX and initialises `ffxProvider_FSR4` is **UNVERIFIED** — the project has never observed 4.1.1 initialise anywhere.
6. **FSR 4.1.2 is not in this build and is not in any released SDK.** The 4.1.2 upscaler revision was observed inside the Adrenalin 26.10.1 package by community reporting; FSR SDK 2.4 (which would carry it plus Vulkan support) is unreleased, with users attributing the delay to a 4.1.2 build in preparation. Our vendored plugin is 4.1.1. Treat "FSR 4.1.2" as a *driver-side* revision, not something the project can call.
7. **Vulkan FSR 4 status.** AMD announced FSR 4 Vulkan support on 2026-10-20 as part of the same newsroom event; the ecosystem places it in FSR SDK 2.4 with no date. **UNVERIFIED** release timing.
8. **The Deck has never been exercised.** Every Deck-profile data point in `upscaler_proof_log.txt` was produced on the laptop's RDNA 2 iGPU. Deck-specific claims in this doc are limited to observed hardware/OS/Proton facts and to AMD's published requirements. Deck performance is **not** characterised by any measurement in this project.

## 6. Bottom line

- **Ship on the Deck with FSR 3.1.5 at 50% render scale (640×400 internal → 1280×800).** FSR 4.x is unreachable there on hardware, delivery, and API grounds simultaneously, and none of the three will change before FSR SDK 2.4 ships.
- **Build and test on MAIN (RX 7900 XTX, Adrenalin 26.10.1)** — it is the only node whose silicon is FSR 4.1.1-eligible — but the engine is not on that node yet, and FSR 4.1.1 has never been observed to initialise on any hardware in this project.
- **The laptop stays test-only.** It is where the verification runs actually happen, and its RDNA 2 iGPU is a reasonable proxy for the Deck's tier (3.1.5) but not for MAIN's (4.1.1).
- **HTPC is unassigned** and has no engine, Steam, or Proton; it is not on any critical path.
- **Do not plan around RDNA 3.5 APU FSR 4.1** until the McAfee/Azor contradiction is resolved in AMD's own words; the 26.10.1 driver shipping FSR 4.1 to Ryzen AI Max/AI 9 parts suggests a "yes" is landing in practice even as the messaging was inconsistent.
